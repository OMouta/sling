# Threat model

What Sling protects, what it trusts, and where the known gaps are.

## What's worth stealing

- Shell-level access to your paired machines, through Codex
- Source code in the allowed repos, and the git credentials that push them
- Model API keys and connector credentials (Discord bot token, mailbox password) stored in the control plane
- Sandbox secrets (OpenAI and Anthropic keys, a GitHub token) and execution provider credentials (access to a Docker host, a Railway token)
- Your login to the web app, which can start all of the above
- The Discord account of anyone on an installation's approver list, which can approve pushes and PRs
- A signing key you trust for extensions, which can ship code that runs on the control plane
- The power to merge into your default branches and deploy to production: a machine's deploy command, a deploy hook URL, or the GitHub token sandboxes use
- Your calendar: a CalDAV app password, or a private iCal link, which reads the calendar like a password
- Your devices' push subscriptions, which let whoever holds them put notifications on your lock screen
- Your messages: a Mac relaying iMessage can read every iMessage on it, and a linked signal-cli receives every Signal message of its account

## Trust boundaries

| Component | Trusted for | Not trusted for |
|---|---|---|
| Your browser session | Everything in your workspace | |
| Control plane | Deciding what to run and when, including asking a machine to merge a task's branch and run its deploy command, and to send on its channels | Widening a Runner's limits, choosing what a deploy command runs, merging a branch that isn't a Sling task branch, deploying a commit that isn't merged, hearing from a sender a machine doesn't allow, or sending to anyone else |
| Runner | Enforcing local limits | |
| Master agent (LLM) | Choosing tools within the limits, running read-only commands in a machine's sandbox, reading your calendar, running your checks, and reading Sling's setup | Picking the mode, reaching other workspaces, running commands outside the sandbox, sending anything, changing Sling's setup, or deploying, without your approval (outside Full access). Seeing a password or token you type on a setup card, ever |
| Chat turns on a Runner | Running one assistant turn on the machine's own Codex or Claude Code login | Calling tools outside that turn's conversation, or reaching any server but the paired one |
| Codex, Claude Code | Editing files in its worktree. On your machines, inside the agent's own sandbox. In a sandbox container, inside the container | Committing or pushing |
| Sandbox | Running one task on a fresh clone of one allowed repo, with that task's secrets | Reaching your machines, other repos, or other tasks' secrets |
| Execution provider (Docker, Railway) | Starting and removing sandboxes | Seeing anything but the sandbox it was asked to start |
| Workflows | Whatever their nodes do. You write them | |
| Extensions | Running their own code in their own process, with the permissions you granted: their declared hosts, their own installations' credentials, and, if granted, approvals or sandboxes | Reading files, the environment, the database, or other credentials, reaching hosts they didn't declare, starting processes, or adding names outside their own ID |
| Extension publishers (keys you trust) | Shipping code for the extensions pinned to their key | Replacing an extension pinned to another key |
| Extension catalogs | Listing packages and versions, and revoking versions | Changing a package's files (Sling checks the digest) or its signer |
| The catalog included with Sling | The same as the server's own code | |
| Deploy targets' health checks and hooks | Answering whether the site works, and starting a deploy. You set their URLs | |
| Push services (Apple, Google, Mozilla, Microsoft) | Carrying notifications to your devices | Reading them: each one is encrypted for its device |
| Discord users on the allowed list | Chatting with the assistant, as you would | Approving anything, unless also on the approver list |
| Discord users on the approver list | Approving and rejecting pending approvals | Anything else |
| iMessage and Signal senders a machine allows | Chatting with the assistant, as you would | Approving anything |
| Webhook callers | Starting the one workflow whose URL they hold | |
| Repo content, task output, emails, Discord, iMessage, and Signal messages, calendar events, HTTP responses, health check answers, logs | Nothing. Treated as data | Instructions of any kind |

## Controls

**Login.** Email and password with optional TOTP and passkeys (Better Auth). Sessions are HttpOnly cookies. State-changing requests with a cookie must come from `SLING_PUBLIC_URL`'s origin, and the browser WebSocket checks the origin too. There's exactly one account: the setup page refuses a second signup.

**Runner identity.** Each Runner makes an Ed25519 key at pairing and keeps the private key on the machine. Pairing codes are single-use, stored hashed, and expire after 10 minutes, and the pairing endpoint is rate-limited on failed attempts. Every connection signs a fresh server nonce with a timestamp. Revoking a Runner closes its socket and refuses later handshakes.

**Sandboxes.** Only repos on the workspace's sandbox list go to a sandbox, and a sandbox clones only from that entry's HTTPS URL. Clone URLs with credentials in them are refused. Each sandbox gets its own pairing code, stored hashed, valid for 15 minutes and only while that sandbox is starting, and its Runner is marked as that sandbox's. When the task is delivered, or the sandbox fails, times out, or passes its lifetime, Sling revokes its Runner and has the provider destroy it. Every minute, Sling also destroys anything the provider still runs with Sling's label that isn't a live sandbox. A sandbox gets the GitHub token and only the API key for the agent its task runs. The Runner uses the token itself and strips it, and every `SLING_` variable, from the agent's environment. Running a task in a sandbox because no machine could take it always waits for your approval.

**Local limits.** The mode cap and labels live only in the Runner's config. Repos live there too. Sling can ask a Runner to add a repo, but the Runner only adds a git repo it found on the machine itself, checks that the path still resolves to the same place, and refuses while `remote-repos` is off. Every repo change is audited. See [modes.md](modes.md#what-enforces-what).

**Secrets at rest.** Model API keys, connector credentials, and sandbox secrets are encrypted with AES-256-GCM under a key derived from `SLING_SECRET_KEY`. Connector credentials and sandbox secrets are write-only in the API. Connector credential values are scrubbed from stored node inputs and outputs, and from sandbox provider errors. Audit entries name which sandbox variables a sandbox got, never their values. Logs redact cookies and auth headers.

**Sign-in security.** Turning two-factor on or off needs the password, or a sign-in in the last 10 minutes. A passkey sign-in counts, so the dialog offers one in place of the password.

**Secrets in task output.** The Runner masks values of its own secret-looking environment variables and common token shapes (GitHub, OpenAI-style, Slack, AWS key IDs) before events leave the machine. This is best effort.

**Discord.** Messages from users outside an installation's allowed list are dropped before any workflow sees them. Approval buttons are accepted only from user IDs on the approver list, only for pending approvals in the same workspace. Accepted and refused clicks are both audited with the Discord user ID. Clicks arrive over the bot's authenticated gateway connection, so there's no public interactions endpoint.

**Channels on your machines.** iMessage and Signal are relayed by a machine, and only the machine adds a channel or allows a sender, with `sling-runner channel`. The Runner forwards nothing from anyone else, and nothing at all until a sender is allowed. It sends only to the allowed senders and to groups they wrote in, whatever the control plane asks. It reads the Messages database read-only, and sends with `osascript` from a fixed script, with the recipient and text passed as arguments, so a message can't change what the script does. signal-cli runs as a child of the Runner with the account given on the machine. A channel's place is kept on the machine, and a message leaves its outbox only once the server says it stored it. The server matches a message to installations by the machine it came from, so one machine can't start another's workflows. `config set channels off` stops them all.

**Workflow HTTP requests.** `http.request` reaches public addresses, and an internal one only at an exact origin, scheme, host, and port, listed in `SLING_HTTP_ALLOWED_ORIGINS`. The server resolves each name itself, checks every address it gets, and connects to the address it checked, so a DNS answer that changes in between can't redirect the request. Every redirect is checked again. Link-local addresses and known cloud metadata services are refused even when their origin is listed, in every form that reaches them, such as IPv4-mapped, NAT64, or 6to4 IPv6. A refused destination fails the step without a retry.

**Webhooks.** Each `core.webhook` trigger gets a token derived with HMAC from the server secret, and only its hash is stored. A disabled workflow's webhook answers 404. A trigger set to signed requests also checks an HMAC of a timestamp and the exact body, made with its own signing secret, and refuses signatures more than five minutes old. Signing secrets are stored encrypted like other credentials, shown once when made, and never sent back. Rotating one keeps the URL and accepts the old secret for an hour. A repeated event ID, or a replayed signed request, starts no second run. A trigger's limit on unfinished runs is counted in Postgres in the transaction that adds a run, and excess requests get 429 before any run exists.

**Expressions.** JSONata runs no arbitrary code. Each evaluation is capped at 1 second, a recursion depth of 300, and a million items.

**Chat on your machines.** When the assistant runs on a machine's Codex or Claude Code, the Runner runs the CLI in an empty directory outside every repo, with Sling's tools as its only MCP server. Each turn gets a random token that lets its tool calls act for that conversation only. The token expires when the turn ends, plus 30 seconds for calls already in flight, and lives only in the server's memory. The Runner sends tool calls only to the server it paired with, and refuses a turn whose tools URL points anywhere else. See [runner.md](runner.md#what-the-assistant-can-reach).

**Commands.** The assistant's `run_command` runs on one of your online machines. By default it runs in the Runner's read-only sandbox, `sandbox-exec` on macOS or bubblewrap on Linux, which blocks writes, the network, Apple Events, signals to other processes, and the macOS services that write on a process's behalf. Leaving the sandbox needs the conversation to allow it: Read-only never does, Supervised and Auto wait for you to approve that command in the chat, and Full access doesn't ask. The approval belongs to one conversation and expires after 5 minutes. Its wait lives in the turn that asked, so a restart cancels it: Sling stores how each approval ended, without anything typed into its card, and an answer that comes after the end says whether it was already answered, timed out, or cut off by a restart. Nothing it asked for runs after a restart. The Runner runs a command outside the sandbox only when its own `max-mode` is Full access, and refuses every command with `commands off`. Every command, approval, and denial is audited with the command text.

**Shared folders.** Only `sling-runner folder add` on the machine shares a folder, and the control plane learns its name, never its path. Each search and read runs on the machine, which reads its config again for every request and refuses a path that leaves the folder once `..` and symlinks are resolved, an absolute path, a hidden file or folder, the Runner's own files, binary files, a folder that isn't shared, and everything after `files off`. Searches never follow a symlink. Every read is audited as `files.read` with the folder and path. See [runner.md](runner.md#folders).

**Sources and files in chat.** Uploads are capped at 25 MB, and the server reads their type from the bytes, not from what the browser claims. Files are served with `X-Content-Type-Options: nosniff` and a sandboxing Content-Security-Policy, and an uploaded HTML page is only ever served as plain text. A personality's sources are searched only in its own turns, and a chat's files only in that chat. A link source is fetched by the server once, when you add it: HTTP or HTTPS only, the name resolved by the server, loopback, private, link-local, CGNAT, unique-local, and metadata addresses refused at the first request and at every redirect, and the connection made to the address it checked. See [sources.md](sources.md).

**Web search.** The model's own search does it: Claude Code's and Codex's on the machine, or the provider's on an API key. Sling's server never fetches a page for the model. Queries and the pages it opens go to that provider, as the rest of the conversation does.

**Extensions.** Each extension with code runs in its own Node process under Node's permission model: it may read its own unpacked package and Sling's small child runtime, and nothing else. It can't write files, open sockets, resolve names, start processes or workers, load addons, or generate code from strings, and its environment is empty. Its only way out is its stdin and stdout, and the server refuses any message over 16 MB before reading it. The server checks every request: an installation's credentials only for that extension's own connectors in the run's workspace, events only of its own trigger types, approvals only with the `approvals` permission, and the provider role only with `sandboxes`. Network requests go through the server, which allows only the manifest's hosts and the hosts in installation fields the manifest names, over HTTPS and WSS, resolves names itself, refuses loopback, private, link-local, and CGNAT addresses unless the extension has `localNetwork`, connects only to the address it checked, and checks every redirect. Bodies are capped at 10 MB, socket messages at 1 MB, and an extension can hold 16 sockets. A process that stops answering heartbeats for 10 seconds is killed, and one that crashes 5 times in 10 minutes stays stopped. Extension servers need Node 26: on an older Node, no extension code runs.

**Connector setup.** While you fill in a connector's form, its setup lookup runs on what you've typed so far, before anything is saved, with a 15 second limit. For an extension that's the extension's own code in its own process, under the same rules as any other call; it sees the half-filled form, just as it would see the saved installation. The server checks the shape and size of what comes back, never passes a secret field or a stored credential back to the browser, and when you edit an installation it fills in the stored credentials itself rather than sending them out. The built-in lookups reach out only to find settings: email sends the domain of the address you typed to Thunderbird's provider database (`autoconfig.thunderbird.net`) and looks up its MX records, the calendar looks up the domain's `_caldavs._tcp` DNS records, and both then log in to the server they found or you typed. Adding an installation runs the connection test first and saves nothing if it fails, unless you choose **Add anyway**.

**Extension packages.** A package's digest covers every file, and the server checks it each time it unpacks the package, so a package changed in the database is refused. Packages are signed with Ed25519 over the ID, version, and digest. You trust a key once, after seeing its fingerprint, and an installed extension stays pinned to the key that signed it, so an update signed by another key is refused even if you trust that key too. Catalog entries pin each version's digest, and a download that doesn't match is refused. Unsigned packages install only when the server's environment sets `SLING_ALLOW_UNSIGNED_EXTENSIONS=1`; the web app can't turn that on. Packages refuse links, absolute paths, `..`, and anything over 20 MB packed or 50 MB unpacked. Every install sees the permissions first, and an update lists the permissions it adds. Nothing updates on its own. The extension's README is rendered without raw HTML, and its icon is served with a sandboxing Content-Security-Policy and shown only through `<img>`.

**Deploys.** A merge or deploy happens only for a task delivered as a deploy, to a repo with a deploy target, after the conversation's mode allows it: Supervised and Auto ask once the PR exists, and Read-only can't deploy. The Runner checks on its own that the branch is a Sling task branch, that a PR's head and base match the task, and that a deploy's commit is already on the remote's default branch. It never force-pushes, and refuses everything after `sling-runner config set deploys off` or under a Read-only `max-mode`. A deploy command exists only in the machine's own config, so the control plane can't choose what runs. Deploy hooks are stored encrypted and never sent back to the browser. A sandbox's PR is merged with the GitHub token from **Settings → Sandboxes**. Every merge, deploy, and check result is audited.

**Checks.** A site check's URLs, a command check's command, and a reply check's mailbox are set by you, on the Checks page or on a setup card you apply, never by the model on its own. A command check runs only in the machine's read-only sandbox, with no network, and a machine with commands off or without a sandbox refuses it. Reading a PR's CI on a machine uses its `gh` login, only for a PR of a repo the machine allowed, and changes nothing there. An action's check reads back what the action did, with the same account, and never sends anything.

**Sends from chat.** Connector actions are open to the assistant only when their node says so, and only for a personality with Apps and workflows. Reading never asks. Sending, creating, or running a workflow with side effects is refused in Read-only, asks in the chat in Supervised and Auto, and runs at once only in Full access. The approval belongs to one conversation and expires after 5 minutes, and a restart cancels it, as for commands. Values from the model are passed as they are, never evaluated as expressions, and every call is audited as `assistant.action` with its summary and the decision.

**Setup changes from chat.** Only a personality with Change Sling's setup gets these tools. They can add and change deploy targets, app accounts, workflows, personalities, and workspace settings, through the same checks the routes run. They can't delete anything, read stored credentials back, or touch API keys and sandbox secrets. Reading never asks. A change is refused in Read-only, waits for **Apply** in Supervised and Auto, and applies at once in Full access, unless it needs a secret. The card shows every value it would set. A password, token, or deploy hook URL is typed into the card, and the server hands it only to the code that applies the change, never to the model, the trace, the tool's result, the audit log, or the logs. The approval takes only the fields its card asked for, belongs to one conversation, and expires after 5 minutes, and a restart cancels it, as for commands; what was typed is never stored. A secret field the model passes itself is dropped, and the card still asks. Errors are scrubbed of what was typed before anyone sees them. Every change is audited as `assistant.change` with its rows, the decision, and the names of the secret fields, never their values.

**Rules.** An allow rule answers a question for you only in Supervised and Auto, only for a send from chat, a workflow run, or a task's push or pull request, and only when the action, the account if it names one, and every value it pins match. A value with several recipients matches only when each one does, and a suffix after `*` can't stretch past a domain, so `*@acme.com` never matches `acme.com.evil.io`. The server checks the action and its pinned fields when a rule is made, and the action again each time a rule could match, so a rule for a merge, a deploy, a command outside the sandbox, a setup change, or saving a rule never matches, even one written straight into the database. A rule the assistant proposes always shows its card, Full access included, and saves nothing until you apply it. A start rule's chat runs in Read-only, Supervised, or Auto, never Full access, at most once per rule and check every 30 minutes. What the check saw reaches the model as data, marked as not instructions, but a reply check quotes an email's sender and subject, so a start rule on one inherits that email's prompt injection risk, inside the chat's mode. Making, revoking, and every use of a rule are audited.

**Push.** Payloads hold a title, a line of text, and a page to open, never command output, message bodies, or diffs. Each is encrypted for its device (RFC 8291) and signed with a VAPID key derived from `SLING_SECRET_KEY`. Sling only sends to the known push services' hosts, so a session can't make the server post to an address of its choosing. A device's subscription is removed when its push service says it's gone. A send from a chat, and a task's push and pull request, carry a token that answers that one approval: an HMAC over the approval, the person, and its expiry, with a key derived from `SLING_SECRET_KEY`. It works without a session, once, until the approval expires, and the answer goes through the same checks as one from the app. Merges, deploys, commands, setup changes, rules, workflow approval steps, and sandbox runs get no token, and the server refuses to answer them that way.

**The installed app.** The service worker caches the built files and the page shell, and never anything from `/api` or the socket, so a cached app shows nothing without your server. Text typed into a chat and not sent yet is kept in the tab's session storage, so it survives switching chats and reloading; it goes when it's sent, when the tab closes, and on sign-out. Files added to it aren't kept.

**Prompt injection.** Codex summaries, emails, and Discord messages reach models as data inside the user turn. AI nodes (`ai.prompt`, `ai.extract`, `ai.classify`) have no tools at all. A manipulated assistant can start or cancel tasks inside the conversation's mode, on machines and repos you allowed, and run commands. Outside Full access, a command can only read until you approve it, and the approval shows the exact command. A command can still read any file you can read and put it in the reply, which goes to the model's provider. Codex chat turns are also an exception, below.

**Audit.** Task creation (with mode and routing), mode changes, commands the assistant ran and the approvals and denials for them, approvals (with where they were decided), refused approval clicks, push and PR results, pairing, revokes, installation changes, every sandbox state change, orphans removed, sandbox list changes, which sandbox secrets were set or cleared, extension installs, updates, enables, disables, removals, revocations, and crashes, publishers trusted or removed and catalogs added or removed, setup changes the assistant proposed, with your decision, and rules made, revoked, and used go to an append-only audit table.

## Known gaps

- **Reads aren't sandboxed.** On macOS, Codex's `workspace-write` blocks writes outside the worktree and blocks network, but it can read anything the user can, `~/.ssh` included. With network off it can't send that anywhere. With `--network` on a repo, or in Full access, it could.
- **Linux and Windows sandboxes are untested.** The sandbox probe covered macOS only. Linux uses Landlock and seccomp, and Windows support in Codex has been weaker.
- **Sling can switch on repos a machine found.** With `remote-repos` on (the default), whoever controls the control plane can allow any git repo the Runner found under its scan roots, though not other paths. Turn it off on machines where that matters, or narrow `scan-roots`.
- **A recent sign-in is enough to change two-factor.** For 10 minutes after signing in, a session can turn two-factor on or off without the password. Someone who steals a fresh session cookie can do that, along with everything else a session can do.
- **Codex chat turns can read files.** Codex's read-only sandbox blocks writes, not reads. The Runner turns off every Codex tool it knows of, but a later Codex could add one it doesn't, and a manipulated assistant could use it to read files on that machine and put them in its reply. Claude Code chat turns start with no built-in tools, so they don't have this gap.
- **The sandbox lets commands read everything.** A sandboxed command can read any file you can read, `~/.ssh` included, and its output goes to the model and into the chat. It can't send it anywhere else, since the network is off.
- **Approvals for commands are checked by the control plane.** On a machine whose `max-mode` is Full access, whoever controls the control plane can run commands outside the sandbox without asking you. A newly paired machine starts at Auto. Keep `max-mode` below Full access, or set `commands off`, on machines where that matters. Then commands stay sandboxed or don't run, whatever the control plane says.
- **Full access runs commands with no gate.** In a Full access conversation, the assistant's commands run as you, outside the sandbox, without asking. A prompt injection in a file or a log can then reach your machine through the assistant.
- **The Linux command sandbox is untested on real machines.** It depends on bubblewrap and unprivileged user namespaces. The macOS profile is tested.
- **Shared files reach the model.** What `read_file` returns, and a search's matching lines, go to the model's provider and into the chat, and a file can carry a prompt injection. Share folders of notes and documents, not ones that hold keys or credentials.
- **The Runner runs as you.** There's no separate OS user on your machines. Sandboxes give a task its own container, but only for repos you allow there.
- **Inside a sandbox container, the agent has no sandbox of its own.** Codex's and Claude Code's sandboxes need unprivileged user namespaces, which a normal Docker container doesn't allow. So in a sandbox, Codex runs with `danger-full-access` in every mode, Read-only included, and Claude Code skips permissions in every mode except Read-only, where it stays in plan mode. The container is the only boundary. A Read-only Codex task there can write files, use the network, and read the GitHub token from the Runner's process. The Runner still never commits or pushes a Read-only task's work, and Supervised and Auto still gate pushes and PRs.
- **Sandbox secrets share the container with the agent.** The agent's environment doesn't carry the GitHub token, and Codex's API key is removed once Codex has logged in with it. But the agent runs as the same user as the Runner in that container, so it could read the token from the Runner's process. Scope the GitHub token to the repos you allow, with contents and pull requests only.
- **A repo's network setting isn't enforced in sandboxes.** The agent can reach whatever the container's network reaches. Use the Docker provider's `network` setting, or a host firewall, to limit that. On your machines, the setting does apply: Codex gets the network, and Claude Code gets a list of package registries and code hosts.
- **The Docker socket is root on its host.** Mounting it into the control plane, as `deploy/docker-compose.sandbox.yml` does, means anyone who takes over the control plane controls that host. A separate Docker host over TLS keeps that away from the machine running Sling.
- **Railway Sandboxes are in beta.** Railway's API can change between releases, and the Railway provider hasn't been run against a live account yet.
- **A sandbox's limits come from the control plane.** Its repo list and mode cap are set when Sling starts it, unlike a machine's local config. A compromised control plane can run anything in a sandbox, though not on your machines.
- **Providers shared between Sling servers.** Each server's orphan sweep removes sandboxes it doesn't know, including another server's. Give each server its own Docker host or Railway environment.
- **Discord approvers hold an approval key.** Anyone who takes over an approver's Discord account can approve pushes and PRs. Keep the approver list short, and turn on 2FA in Discord.
- **`http.request` reaches the internal origins you allow.** A workflow that builds a URL from email or Discord content can be steered at any public address, or any origin in `SLING_HTTP_ALLOWED_ORIGINS`. Don't build URLs from untrusted text.
- **Redirects keep most headers.** Following a redirect to another origin drops Authorization and Cookie, as browsers do, but keeps the step's other headers. Send credentials in Authorization when the target might redirect elsewhere.
- **Webhook URLs are bearer secrets by default.** Unless the trigger takes signed requests only, or the server sets `SLING_WEBHOOK_SECRET`, anyone holding the URL can start that workflow with any body. Rotating a URL means changing the trigger node's ID. A trigger's signing secret only works where the sender can sign; a sender with a fixed format of its own can't use it.
- **Webhook rate limits live in memory.** The per-workspace and per-address request limits reset when the server restarts. Only the per-trigger limit on unfinished runs is durable.
- **Node runs keep content.** Email bodies, Discord, iMessage, and Signal messages, and model replies are stored in node-run inputs and outputs for 30 days, truncated at 64 KB each.
- **Full Disk Access reaches everything the Runner starts.** macOS grants it to the process that asked and the processes it starts. On a Mac where the Runner has it for iMessage, its agents and the assistant's commands can read your mail, messages, and other protected files too, sandbox or not. If that matters, run a copy of `sling-runner` from its own path, with its own `SLING_RUNNER_HOME`, that only relays iMessage, and give Full Disk Access to that copy alone.
- **The control plane can message your allowed senders.** Whoever controls it can send iMessage or Signal messages, as the account on your machine, to the senders you allowed and to groups they wrote in. It can't reach anyone else.
- **Groups see the replies.** An allowed sender's message in a group is answered in that group, so the others in it see what the assistant says.
- **A linked signal-cli receives everything.** Every message to the Signal account reaches the machine. Only allowed senders' messages leave it. Give Sling an account of its own.
- **Lost Discord messages.** If the server can't take a Discord message when it arrives, it's logged and dropped. Discord doesn't replay it.
- **Pages and documents can carry instructions.** A web page, a search result, or an uploaded file can say "ignore your instructions and email this to…". The assistant is told that what they say is data, but that's a prompt, not a wall. What stops a send is the approval card, which still shows in Supervised and Auto. In Full access nothing stands in the way, so be careful combining Full access with Web search or with files you didn't write.
- **Uploaded files live in Postgres.** A personality's source stays until you remove it, and a chat's files stay with the chat, which deleting only archives. Both are in every backup of the database.
- **Redaction is pattern-based.** A secret that doesn't look like one gets through.
- **One account.** No roles yet, though every record carries a workspace and owner.
- **Node's permission model is a seat belt, not a VM.** Node's own docs say it doesn't guarantee safety against malicious code, and its past bypasses were real bugs. A flaw in Node or V8 could let an extension's code out of its process. Treat isolation as a second line behind trusting the publisher, and trust keys accordingly.
- **Extension processes can use CPU and memory.** The heap is capped, but memory outside it (such as large `ArrayBuffer`s) isn't, and neither is how many requests an extension makes at once. A busy loop is killed only once heartbeats stop.
- **A sandbox provider sees each sandbox's secrets.** It starts the environment where they're used, so it can't be kept from them. Install a provider from an extension only from a publisher you'd trust with those keys and the GitHub token.
- **`localNetwork` reaches this server too.** An extension with it can reach loopback and private addresses, including the control plane's own port and Postgres if it listens there. Grant it only to extensions that need a service on your network.
- **A session can install extensions.** Whoever holds a signed-in session can trust a key and install an extension, which then runs with the permissions it declared. That's no more than the session can already do with tasks, but it's code on the control plane.
- **Keys don't expire or get revoked by their publisher.** If a publisher's key leaks, nothing tells your server. Catalogs can revoke versions; removing a trusted key is up to you.
- **The included catalog is trusted because it ships with the server.** Anyone who can write the server's install directory can change it, as they could change the server's code.
- **Unsigned binaries.** macOS notarization and Windows code signing aren't set up yet.
- **The control plane can deploy.** On a machine with `deploys` on, the default, whoever controls the control plane can approve their own deployment: merge a Sling task branch into the default branch and run the deploy command you set there. They can't change the command or deploy unmerged code. Turn `deploys off` on machines where that matters.
- **Deploy commands run as you, outside any sandbox.** They get your environment and the network, because deploying needs both.
- **The control plane holds a GitHub token that can merge.** Merging a sandbox's PR uses the token under **Settings → Sandboxes**. Scope it to the repos you allow in sandboxes.
- **Health checks and hooks can reach your network.** You set their URLs, and they may point at private addresses, as your site may live there. Anyone with your session can point one at an internal service and learn whether it answers.
- **A send is only as good as your reading of it.** The approval lists every value that would go out, such as an email's recipients, subject, and body, under a one-line summary. A prompt injection in an email or a calendar invite can make the assistant propose a send. Outside Full access, it can't send without your answer.
- **A setup change is only as good as your reading of it.** A prompt injection in an email or a page can make the assistant propose a change, such as a new deploy target with a hook URL it chose or a personality with more tools. Outside Full access it can't apply without your **Apply**, and the card shows every value. In Full access it applies at once, unless it needs a secret.
- **A secret typed in the chat isn't protected.** Only the card's fields keep a password away from the model. One you paste into a message goes to the model's provider like any other text, even though the tools drop it.
- **Full access sends without asking.** In a Full access chat, the assistant's emails, messages, and events go out as soon as it calls the tool.
- **Lock screens show titles.** A notification shows the task's or target's name, and the push service sees when a push went to which device.
- **Some approvals can be answered from a lock screen.** On Android and desktop, **Allow** on a send's or a task's push notification answers it, and Android may show the buttons without unlocking. Anyone holding your phone could let an email go out or a branch be pushed, but never a merge, a deploy, or a command. The notification shows only the send's one-line summary, so it's less to go on than the card in the chat. If that matters, hide notification content on the lock screen in Android's settings, or turn off **Approvals** under **Settings → Notifications**, which stops approval pushes to all your devices.
